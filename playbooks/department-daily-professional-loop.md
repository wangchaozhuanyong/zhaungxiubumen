## 每日共同顺序

2026-10-06 接续修正：共同顺序同时读取 `playbooks/single-primary-task-dispatch-and-undone-report.md`；新有界派工使用 `prompts/department-single-primary-dispatch.md`。部门每轮结束先核验入队合同的顶层固定聊天 ID、真实 `chat_reply`、本轮派工与接单链，再读取准确入队回执；文件校验或短键成功不代表总控收到。总控结束或中断时必须更新 `reports/company-current-work-summary.md` 和详细进度表，列明已做、未做、未派出、未发布、下一负责人和条件。

1. 核对注册表中的本项目、固定任务、准确标题、cwd、分组和健康；读取原任务/唯一主账、最近候选、QA、执行和公开复核回执。正在执行的轮次优先做完，不插入普通消息；同一候选不因新日期重做。
2. 先接续已明确的返工、发布或数据/事实阻断，再检查本岗位的完整责任范围和新变化。明确本次检查分母、覆盖范围、未检范围、证据日期和来源；每天从专业角度问：还有什么必要工作没做、现有方法哪里质量不足、有什么可验证的新机会、为什么目标尚未达到。不能用文件数、关键词归属数或任务关闭数代替效果。
3. 对依赖齐全的高价值事项连续推进候选或实施；独立 QA、精确授权、正确执行通道与公开复核仍逐层记录。外部事实/权限/数据阻断只阻断依赖项，其他安全工作继续。不得为凑日报制造低价值工作。
4. 每天在本部门固定聊天交一次可见结果：完成了什么及证据、未完成及原因、检查到哪里/没检查哪里、新发现或遗漏的方法、指标和趋势、唯一下一负责人及最小动作/解除条件。即使无变化，也报告实际检查范围和 `NO_CHANGE`；没有检查不得写“正常”。同日新完成、失败、阻断或回滚另按准确原任务增量回报。
5. 先写并校验本项目 V2 outbox；有新结果或需决策时，以原 task_id、部门、候选版本和 outbox SHA 登记一次 `notification_queued`，不向 active 或 idle 总控聊天直发消息。派工任务须有原派工和接单链；部门1的固定网站日任务可用合同限定的 `source_mode=scheduled_run`，附当天实际完成的自动化轮次、固定聊天回复哈希和时间，不补造派工/接单。入队失败保留阻断和原证据，不伪造发送。部门不能自行把本部门任务派给其他固定部门。

## 总控每日决策

2026-10-02 QA 接续优先：QA 自动日检开始业务检查前先运行 `python3 tools/qa_dispatch_priority.py`。`RESUME_DISPATCHED_QA` 优先续准确已派任务；`DEFER_DAILY_AWAIT_CONTROLLER_DISPATCH` 只记录候选待总控正式派入并结束本次普通巡检，不自行审核未派候选、补造派工或接单。`BLOCKED_INVALID_PRIORITY_EVIDENCE` 保留准确控制阻断；只有 `DAILY_CHECK_ALLOWED` 才开始普通日检。总控维护 `data/qa-dispatch-priority.json`，每项绑定原任务、候选版本、任务包哈希、真实源 outbox 与收取/决策证明；根据原生精确派工和本版结果自动去重。此规则不取消每日检查，不打断在途工作，不构成 Codex 调度器锁，也不代替现场身份、健康、精确 policy-check 或生产门禁。

2026-10-01结果等待修正：本轮由总控派出且尚未回传的有界任务，总控不得仅因部门`active`就结束自己的接续轮次。完成独立控制工作后，使用Codex `wait_threads`按任务和cursor进行事件等待，每次最多60秒；任务完成或需关注即核原聊天与持久队列，登记收取、决策及实际下一动作，继续原链。超时只是仍在运行，不能补造回执或重复催发普通消息。用户新输入、中断或真实运行限制出现时先留准确task/turn/cursor及尚待阶段；恢复后先收新结果，再接原任务。只有没有本轮内部依赖可接续，或有具名外部输入阻断/实际运行限制时才结束。该规则不增加五分钟轮询、不向活跃聊天推送结果，也不声称项目文件能自动唤醒已经结束的总控；每日18:00仅用于独立日检或中断后的漏报兜底。


总控还必须处理 `followthrough_results`：除已验收的 `close_scope` 外，写完 `controller_decision` 仍是待办。实际派工后用原任务结果身份记录 `controller_followthrough=dispatch_sent` 并引用**决策之后**命中下一负责人的真实 `dispatch_sent` 回执；走发布路线时只有实际执行及 PASS 公开复核回执才可记 `execution_verified`。外部等待或后续阻断写具名解除条件和下次检查时间，到期重新进入待办；总控自身完成的控制动作引用项目内证据。`pending_count` 只计未决策结果，`followthrough_pending_count` 计决策未落地或到期复查，排队要看 `total_actionable_count`，不能只看前一个数归零。

阻断或等待未到复查时间时显示 `waiting_followthrough_review`，这表示该控制动作仍未解决。恢复现场身份、健康或权限后，沿**同一结果身份**凭新的项目内证据追加后续动作：仍受阻可记录更晚的检查点；真正派出后引用新的 `dispatch_sent` 回执。相同证据不得刷写，相同任务包不得重发，已落实的后续动作不得重复登记。复查时间只是防漏，不代替专业部门当轮主动交付和总控接续。

## 2026-10-02 结果入队字段与冻结顺序

当前 queue 门禁要求与普通 V2 校验不同。派工任务须写明并让部门实际核验以下字段：outbox 顶层 `fixed_chat_task_id` 为注册固定聊天、`candidate_version` 为本版；`chat_reply.nonempty=true` 和 `chat_reply.in_current_fixed_department_chat=true` 只在本轮固定聊天已有实际非空结果回复且现场身份/轮次核实后记录，附准确原消息/轮次引用、回复SHA和原观察时间，不保存正文、不把接单回复冒充结果。普通 `validate_outbox` 通过不代表这些 queue 条件已经通过。

正确顺序为实际聊天回报 → 核实并填准确回复元数据 → 保存最终V2并校验 → 计算该最终outbox SHA → 沿本轮真实 dispatch/chat_ack 登记一次 `notification_queued`。入队后不覆盖冻结outbox。字段遗漏导致失败时保留失败回执和旧文件，生成只修元数据的新V2/新hash后入队，候选内容不重复制作；不得只把字段改为true而没有原聊天证明。QA的每版结果仍需准确native qa_verdict/action/candidate，结果入队不自动完成业务验收。

对口协调者收取时核验原回复、最终hash和阶段，登记收取、决策与真实下一动作；不向总控插消息、不恢复高频轮询。

## 2026-10-06 结果队列幂等键长度

结果登记的 `idempotency_key` 最长 200 字符。新回执统一调用已验收的只读 `tools/result_handoff_key.py`；其 digest 按实际实现的有序数组 `[event, task_id, sender_department, candidate_version, result_sha256]` 使用紧凑 `ensure_ascii=True` JSON 的 UTF-8 SHA-256，输出 `rh-<event>-<digest>`。不要手工另换字段顺序生成第二套键。此说明只规范新回执，旧成功键保持原样。同一最终结果同一事件得到同一键；先冻结最终 V2，再计算哈希与键。短键 helper 不验证完整入队资格。保留旧失败证据，不重发已入队结果、不重制未变候选、不放宽原派工/聊天/健康/QA 门禁。
