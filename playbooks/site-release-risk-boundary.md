# FLASH CAST 网站常规优化自动放行边界

## 目标

让内容、SEO 与网站增长部每天能够真实推进并发布常规优化，同时把会影响网站可用性、业务承诺、数据、费用或其他项目的动作留给老板决定。判断标准采用“合理确认”，不追求与改动无关的全站完美。

## 固定角色

- 内容、SEO 与网站增长部：提出精确候选、提供事实依据、字段级或文件级 diff、完成匹配风险的检查，并负责获准后的实施与公开复核。
- 质检部：判断候选是否存在 P0 或与本次范围直接相关的 P1；不因无关数据缺失或轻微 P2 阻止发布。
- 运营总控：依据本文件给出 `AUTO_RELEASE`、`REWORK` 或 `OWNER_APPROVAL_REQUIRED`。运营不代写专业内容，也不代替 QA；命中常驻授权时由政策层生成单次精确许可。
- 老板：只处理 R3、授权外动作、业务事实选择或无法安全回滚的重大变更。

## 风险等级

### R0：内部工作，自动执行

只读检查、关键词 Mapping、审计、草稿、brief、内部链接图、机会清单、报告、备份和 dry-run。无需 QA 或老板批准，但不得冒充已发布。

### R1：常规 CMS 内容，运营自动放行

满足以下范围之一：

- 修改已有 URL 的正文、Title、Meta Description、H1/H2、FAQ、图片 alt、同站内链或 CTA 文案；
- 每日最多发布一个新的中英双语 Blog 组合；
- 一个连贯批次内最多修改 20 条现有 CMS 记录。

同时必须满足：公司事实已确认；目标 URL 和字段级 diff 精确；中英文匹配；不改 slug、发布状态、canonical、noindex、重定向、导航、表单目的地或联系方式；无 P0、无与本次范围相关的 P1；有发布前快照、回滚目标和发布后公开读取验证。

R1 不要求全站 CI。纯文字、Meta、FAQ、alt 或已有站内链接调整，只检查目标记录、HTML/链接格式、中英页面和发布后公开输出。缺少 GSC、GA4 或销售数据不能阻止 R1，只能阻止排名、流量、线索或成交结论。

### R2：低影响网站代码，运营自动放行

限于装修网站仓库中的常规 SEO/CRO 代码：Meta/Schema 内容映射、已有 URL 的内链生成、双语显示、页面文字展示、非关键样式和 CTA 展示。不得涉及 R3 项。

发布前最低检查为：准确 diff、受影响测试、typecheck、build、双语目标页抽查、QA PASS、干净发布源、可回滚提交、同一 main SHA 部署和发布后受影响页面复核。QA 首次发现 R2 缺陷时，内容、SEO 与网站增长部可以先在隔离工作树制作最小修复候选、运行相关检查并准备备份/回滚证据；这一步不要求预先 QA PASS，但不得合并、部署或发布。只运行与改动风险匹配的检查；已经通过且代码未变的检查不重复执行。

### R3：必须老板批准

包括：Google Ads 或任何费用；客户联系；价格、合同、工期、保修、资质、案例归属或未确认业务事实；硬删除/取消发布；核心 URL 的新增、合并、slug、redirect、canonical、noindex 或 sitemap 规则；一次超过 20 条公开记录或超过一个新双语页面组合；全局导航、表单提交/送达、追踪标签、数据库 schema、认证/权限、密钥、依赖/构建/部署配置、DNS/基础设施；无法安全回滚；以及任何其他项目。

## QA 的“基本没有大问题”标准

满足以下条件即可放行：

1. P0 为 0；
2. 与本次改动直接相关的 P1 为 0；
3. 事实、目标、diff、双语和回滚证据齐全；
4. R1/R2 对应的必要检查通过。

P2 默认不阻断，记录负责人和最迟三个日检周期内的处理日期。GSC/GA4/销售数据缺失只阻断依赖这些数据的效果结论；浏览器暂不可用时，非布局型 R1 可用 CMS 回读、公开 HTML 和链接检查替代，布局、表单或交互改动仍需受影响视口/流程验证。QA 返工后只复核改动项和原阻断项，不重新扩大成全站审计。

## 每日闭环

`10:30 内容部产出与流量分析 → 13:00 QA → 14:00 运营风险判断 → 14:30 内容部发布或返工 → 15:00 总控最终汇报`

### 防止审核后漏掉执行交接

- 运营初始化任何拟发布任务时，必须同时登记原内容部门（候选负责人及发布执行人）和原 QA 部门，并声明内容交付先于 QA；不能只登记 QA 后便把内容发布当作已安排。
- 收到内容交付后，由运营核对原窗口回复与 outbox，并主动派给原 QA。QA PASS 后运营完成 R1/R2 放行，原内容部门本人取得精确许可、执行发布与公开复核；不得要求老板在部门窗口之间转述结果或重复回复“继续发布”。
- 已存在的 QA-only 历史工作流不能改写原请求、伪造执行部门或把内容执行登记为 QA。可以建立带 `parent_task_id` 的项目内关联发布阶段，继续使用原固定部门窗口、原候选和原 QA；QA 只确认文件哈希与执行范围一致，不重复审查未变化的内容。关联阶段不是新 Codex 聊天，不更换固定窗口或自动任务。
- 老板明确要求当场继续发布时，按同样门禁在当前执行回合收口，不必等下一日检时间；定时任务的原时间保持不变。中断后先读取已有执行/复核回执和线上版本再续接，禁止再次消费已使用许可或重复写入已完成记录。
- 运营只有取得后台保存/生产版本证据及公开复核结果后才汇报“已上线”；放行、保存、公开生效和效果提升分别记录。

发布前先锁定唯一通道：现有 CMS 记录的正文、Title、Meta、FAQ、alt 和普通站内链字段使用 `cms_content_candidate → cms_write`，只走受保护 `content-publish`；前端映射、渲染、Schema 逻辑或组件行为使用 `site_code_candidate/site_code_rework_candidate → site_publish`，只走 feature branch、PR、CI、main 和同 SHA 部署。QA 回执必须写明候选动作类和 `flashcast.com.my:` scope；政策层发现 CMS/代码通道不匹配时硬拒绝。一次候选不得为了省事同时改 CMS 和代码；确实两边都需要时拆成两个动作、两份 diff、两次 QA 和两条执行回执。

- QA PASS 分支：`AUTO_RELEASE → 内容部实施/发布 → 公开复核/必要回滚`。
- QA BLOCKED 的 R1/R2 分支：`REWORK → 内容部完成最小修复、相关检查、备份和回滚包 → READY_FOR_REQA → QA 只复核原阻断项 → PASS 后进入下一次发布收口`。缺少 diff、测试、备份或回滚证据是返工部门需要补齐的工作，不得成为“无人继续处理”的终止理由。
- QA BLOCKED 的 R3/授权外分支：`OWNER_APPROVAL_REQUIRED`，不得由部门自行扩大范围。
- 每次 14:30 先处理最早的未关闭 `REWORK`/`READY_FOR_REQA`，再处理当天新候选；沿用原 task_id，并用候选版本区分每次返工。相同阻断项每天最多自动返工两次，避免循环。
- 跨日重试也必须先证明阻断条件发生了变化。若缺的是受保护发布目标、合法权限、可安全恢复的生产版本、已确认业务事实或同一 QA P1，次日不得仅因定时窗口到来就重做候选、重新预演或触发回滚。运营先登记唯一依赖、负责人和可验证的解锁证据；只有目标能力已经部署并通过拒绝测试、权限实际恢复、权属安全恢复目标出现，或新候选消除了原 P1，才允许原 task_id 继续。没有新证据时报告 `NO_CHANGE_DEPENDENCY_BLOCKED`，不消耗新的返工次数。
- 发布失败的回滚只限预先验证过、恢复后仍满足事实与素材权利边界的版本。若旧版本本身不安全，不得为了形式上的“可回滚”恢复它，也不得循环触发同一失败发布；把该动作升级为准确的 R3 前向修复决定。生产回滚、仅本地候选返工、重新部署必须分别记录，不能混称。

- `AUTO_RELEASE`：R1/R2 且 QA 基本通过，政策层用 `owner-standing-flashcast-site-publish-20260906` 生成当次精确许可；不再问老板。
- `REWORK`：R1/R2 存在 P0 或本次范围 P1，且可以由原专业部门做有界、安全、可回滚的修复；写清原 task_id、负责人、允许修改的文件/字段、一个最小修复动作、必要检查和复验条件。原部门必须继续处理并产出 `READY_FOR_REQA`，不能仅重复报告阻断。
- `OWNER_APPROVAL_REQUIRED`：命中 R3 或常驻授权外范围；总控只提交准确页面、动作、影响和回滚方案。
- 发布失败或公开复核出现 P0 时，自动回滚到预先记录的 CMS revision 或上一稳定 SHA，并如实报告。

`QA PASS + AUTO_RELEASE + policy allow` 是当天 14:30 的执行命令，不是“等老板回复”的中间状态。内容部必须继续到正确发布通道和公开复核；只有 R3、授权外、缺少合法权限/OTP、无法安全回滚或外部平台安全重试后仍失败时才可停止。15:00 运营总控必须在发布窗口结束后汇总全部六个固定角色的实际状态，并把“部门交付、QA、放行、发布、生产复核”分开说明。

## 不得降低的硬边界

付费推广保持关闭；不得跨项目；不得虚构事实；不得直接写生产内容表；不得绕过后台/受保护 publisher、Git 身份、权限或回滚；不得把草稿、QA PASS、PR、CI 或 HTTP 200 单独称为发布完成。
