# 明确主任务、逐项回报与遗漏恢复

本项目的内部协调规则，不增加消息、账号、发布或跨项目权限。实际断点与恢复证据：`logs/handoffs/2026-10-06-department-loop-audit/QA-second-explicit-task-not-executed-actual-final-v1.json`。

1. 普通派工每条消息明确一个主 `task_id / candidate_version / action_id`、准确任务包和交付标准。原工作流曾 closed 不取消本轮新候选的准确派工；通用优先队列没有列出也不能替代读取该包。真实门禁拒绝时保留具体错误，不绕过。
2. 部门接单说明准确主任务和本轮范围；结束说明已做、部分完成、未做、失败、所缺输入、证据、唯一负责人和下一动作。明确未执行的子项不能隐藏在“本轮 completed”中。
3. 确需有界组合包时，总控先保存逐项原任务/版本/动作清单；部门逐项确认和回报。任一条消息的发送成功或第一项 PASS 不能替代其他条目的执行证据。普通接续优先采用串行的单主任务，当前部门 active 时只排队。
4. 本轮遗漏沿原 task/版本/冻结包一次有界补跑，另记录真实恢复 action、原发送和实际未执行证据。不得补造原接单、重复制作原候选或重放已发布动作。
5. 部门结果只在固定聊天说明并以最终 V2 哈希短键入项目队列；总控逐项收取、决策、关联真实下一动作。队列文件不会自动唤醒已结束的总控，保留自然接续与每日兜底，不新增高频轮询。
6. 每次总控结束或真实中断前更新固定进度表，并给老板说明本轮成果、仍未完成、实际候选/QA/保存或部署/公开复核阶段、负责人、下一步和等待条件。已完成的控制接续不能继续显示成一条未派任务；业务余项保留。

这里的“一条消息一个明确主任务”不是“每天只做一件事”；当前任务结束且下一项依赖齐全时，仍应马上接续。

结果回读采用 playbooks/result-queue-concurrent-intake-readback.md：总控可在部门收尾时并发收取或决策，不以这两字段已推进判定入队失败。严格按准确身份核真实队列回执，禁止因并发重复派工或回退状态。

有界主任务必须完成当轮交接后释放固定窗口，新增机会先列在结果中交总控决定，不在收尾时另开无界日检。已有每日专业检查保留，日检本身也按原范围回报；这不限制每日可做的任务数量，也不把一轮结束当业务目标完成。总控有依赖齐全的下一准确候选时，重新现场核对并立即接续。

## 当前职责与每轮交接

每天的专业任务先核对本部门原未完范围，再检查已发布范围与新问题；交付应列出专业遗漏、证据和可执行建议。完成检查报告不关闭尚未修复的问题。缺一项真实输入只阻断依赖它的范围，其他有证据的安全工作继续；没有新输入时不重复制作同一候选或重复 Save。

部门每轮结束说明：本轮完成范围、实际修改/保存/发布与公开复核、未完成范围、阻断证据、唯一下一负责人和解除条件。总控核实后留下决策及真实下一动作；准备了任务包但尚未发送的必须标“未派出”，收到候选但尚未保存的必须标“未发布”。总控临时中断时保留原任务、当前轮次与等待游标；恢复先收这轮结果，不能重发原业务包。

总控每次结束的面向老板汇报至少包含“这次做好了什么”“还没做好什么”“哪个部门下一步做什么”“需要什么输入或复查时间”。固定进度表为 `reports/company-current-work-status.md`，每轮另存带时间的报告和不可变 outbox。队列入队不能自动唤醒已停止的总控；总控工作中使用原生结果事件等待，结束后的漏报由自然接续和每日兜底收取，不承诺不存在的后台自动接续能力。

## 新结果入队前的字段与实际回执

2026-10-06 实际排查发现：一般 V2 文件校验与短键 helper 不验证完整入队条件。新 outbox 仅将聊天身份放在嵌套 `fixed_chat` 中，会被入队门禁拒绝；补上聊天 ID 后，仍缺顶层 `chat_reply` 的真实回复标记也会拒绝。因此所有新派工沿 `prompts/department-single-primary-dispatch.md` 明确要求顶层 `fixed_chat_task_id`、本轮 `chat_reply.nonempty` 和 `chat_reply.in_current_fixed_department_chat`，并核对派工后的 V2 与真实接单链。

一般文件校验通过、短键有效、QA PASS、文件存在和写过日报都不能冒充 `notification_queued`。入队失败只修准确回执，不重做未变正文或 QA 候选；保留每次原拒绝和冻结 V2，以新补正版/新哈希恢复。总控核对同一原任务/部门/候选的补正版，关联旧失败证据，不把旧格式漏报变成新业务任务，也不改旧历史准入规则。已入队的准确结果重复接续只读回，不再发送或制作。


### 2026-10-06 实际回复字节哈希补充

固定消息proof必须在工具内从实际read_thread结构化agentMessage.text取原始UTF8字节计算。禁止手工重打正文或SHA、trim、去Markdown和转义归一化后冒充原文哈希；消息ID/字节数相同也不能替代哈希核对。总控按现场原始消息独立计算；发现不一致只退原负责人做新后缀元数据修复，保留旧原件和已通过业务候选，不重做正文或未变检查、不重放旧通知。元数据修复不等于生产准入或发布。
